# 수집서버 TRIP_EVENT 이상 조사 요청

- 작성일: 2026-09-21
- 대상: `PRIM_RAWGPS.TRIP_EVENT` (0=출발 / 1=운행중 / 2=종료)
- 요청자: 위치검증서버(MapMatchSvr) 담당

---

## 1. 요청 배경

위치검증서버가 과금 구간을 판정할 때 `TRIP_EVENT=2`(종료)를 **운행 종료 시점**으로 사용합니다.
그런데 수집된 데이터에서 종료 이벤트가 **직전 틱과 같거나 과거 시각으로 찍히고, 그 뒤에도 주행
데이터가 계속 이어지는** 사례가 확인됐습니다.

위치검증서버는 현재 이를 방어 로직(`IsTrustedTripEnd`)으로 걸러내고 있으나, **데이터 자체를
바로잡는 것이 맞다고 판단**되어 발생 조건 확인을 요청드립니다.

## 2. 확인 요청 사항

| # | 확인 요청 |
|---|---|
| ① | **종료 이벤트 틱의 GPS 시각이 직전 틱보다 과거**로 기록되는 조건 |
| ② | **한 트립에 종료 이벤트가 2회** 발생하는 조건 |
| ③ | 종료 이벤트 틱만 **`DRIVE_STATUS=2`(정차)** 로 고정되는 조건 (속도 28~35km/h 주행 중에도) |
| ④ | **종료 이벤트가 끝내 오지 않는** 트립, **출발만 있고 1틱으로 끝나는** 트립의 발생 조건 |

## 3. 실측 사례 4건

### 사례 1 — 종료 2회 + 직전 틱과 동일 시각

`trip_id = 000370_20260824135458` / `device_key = CAR000427` / 96틱 / 13:54:58~13:59:42

```
seq   GPS시각          TRIP_EVENT  DRIVE_STATUS  SPEED
  3   13:55:07         1 운행중     2 정차        0
  4   13:55:07         2 종료       2 정차        0    ← seq3 과 같은 시각에 종료
  5   13:55:10         1 운행중     2 정차        0    ← 종료 뒤에도 계속
 ...                                                    (92틱 더 이어짐)
 96   13:59:42         2 종료       2 정차        0    ← 두 번째 종료
```

### 사례 2 — 종료 후 35틱 계속, 정상 종료 없음

`trip_id = 000370_20260824140015` / `device_key = CAR000427` / 41틱 / 14:00:15~14:03:21

```
seq   GPS시각          TRIP_EVENT
  6   14:00:27         2 종료                  ← 출발 12초 뒤 종료
 ...                                            (이후 35틱, 14:03:21 까지)
 41   14:03:21         1 운행중                ← 정상 종료가 끝내 없음
```

### 사례 3 — 출발만 있고 1틱으로 종료

`trip_id = 000370_20260824170527` / `device_key = CAR000427` / **1틱**

```
seq   GPS시각          TRIP_EVENT  DRIVE_STATUS  SPEED
  1   17:05:27         0 출발       1            5
```

### 사례 4 — 종료 시각 3초 역전 + 종료 2회 (주행 중)

`trip_id = 000376_20260819140856` / `device_key = CAR000434` / 23틱 / 14:08:56~14:10:01

```
seq   GPS시각          TRIP_EVENT  DRIVE_STATUS  SPEED
 17   14:09:49         1 운행중     0            28
 18   14:09:52         1 운행중     0            28
 19   14:09:49         2 종료       2 정차       28   ← seq18 보다 3초 과거, 주행 중인데 정차
 20   14:09:55         1 운행중     0            29   ← 종료 뒤에도 계속
 21   14:09:58         1 운행중     0            35
 22   14:10:01         1 운행중     0            35
 23   14:10:01         2 종료       2 정차       35   ← seq22 와 같은 시각, 두 번째 종료
```

## 4. 공통 패턴

네 사례에서 관측된 공통점입니다.

1. **종료 틱의 GPS 시각이 직전 틱과 같거나 과거**입니다 (사례 1·4).
2. **종료 틱만 `DRIVE_STATUS=2`(정차)로 고정**됩니다. 사례 4는 `SPEED_KMH`가 28~35인 **주행 중**인데도
   정차로 기록됐습니다.
3. **종료 이후에도 같은 `TRIP_ID`로 주행 데이터가 계속 이어집니다.**
4. `RECV_DT`(수신 시각)는 네 사례 모두 동일 배치 시각이라, **수집 지연이 아니라 이벤트 생성 시점의
   문제**로 보입니다.

이 패턴은 **종료 이벤트 틱이 정상 주행 틱과 별개로 생성·삽입되면서 시각·상태값이 직전 틱을
따라가지 못하는 것**으로 해석됩니다. 확인 부탁드립니다.

## 5. 위치검증서버 측 영향

| 현상 | 영향 |
|---|---|
| 종료 2회 | 첫 종료로 과금 세션이 마감되면 이후 주행 구간이 끊깁니다. 현재는 시각 역전을 근거로 첫 종료를 무시하도록 방어하고 있습니다 |
| 종료 없음 (사례 2·3) | 정상 종료가 아니므로 **TTL·트립전환 강제마감**으로 처리되어, 과금 이력이 `CHARGE_YN=N` / `CHARGE_STATUS=3`(심사 대상)로 남습니다 |
| 주행 중 `DRIVE_STATUS=2` | 정차 여부를 이 값으로 판단하지 않도록 이미 설계를 바꿔둔 상태라 직접 영향은 없습니다 |

현재 방어 로직으로 과금 금액에 오류가 생기지는 않으나, **사례 2·3처럼 정상 종료가 없는 트립은
심사 대상(N/3)으로 남아 수작업 확인이 필요**합니다.
